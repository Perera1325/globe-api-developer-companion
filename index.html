Overview

The GLOBE Elasticsearch API (api.globe.gov/search/) is a public, read-only API for querying citizen-science environmental measurements submitted through the GLOBE Program. This dashboard summarizes what the official documentation page and the GLOBE Data User Guide state, so developers can integrate with it without re-discovering the same gaps.

Documented Endpoint Groups

Public API

Measurement data queries, filtered by protocol and a date field/range.

Public API endpoint summary
MethodPath patternPurpose
GET /v1/measurement/{protocol}/{dateField}/ Query measurements for one of 53 documented protocols (e.g. aerosols, land_covers, soil_phs), filterable by date range, country, GLOBE team, lat/lon, organization, site, polygon, and user ID.

14 GET endpoints are documented under this group in the live OpenAPI spec (tag v-1-controller).

Public Dev API

Auxiliary reference metadata supporting the main measurement API.

Public Dev API endpoint summary
MethodPathPurpose
GET /dev/country/all/ All country reference data.
GET /dev/lastpublishdate/ Last published date for the dataset.

The HTML docs page additionally describes this group as covering “a list of all countries, places, last published dates and more,” but the live spec defines only the two endpoints above — no “places” endpoint exists in the current spec. See Documentation Gaps.

Note: the response-shape schemas this project ships for these two endpoints (schemas/dev_country_all.schema.json, schemas/dev_lastpublishdate.schema.json) are illustrative and non-authoritative — best-effort guesses, since no live request was made to either endpoint and the official spec documents no response fields for them either. Do not treat them as a confirmed contract.

Common Integration Errors

  • Treating userid as identifying. It is a numeric, opaque ID, not an email or username — do not use it to look up or display a person's identity.
  • Assuming a strict response schema. The live OpenAPI spec declares the response model as an empty object (no documented properties). Field names you rely on come only from the PDF Data User Guide; validate defensively (see the validator/ tool in this repo) rather than assuming a field will always be present.
  • Assuming 401/403 means real authentication exists. Both the Public API and Public Dev API specs declare 401 Unauthorized and 403 Forbidden as possible responses on every operation, but no security scheme (API key, OAuth, Basic Auth) is defined anywhere in the spec or documentation. This may be generic framework boilerplate rather than a real access-control boundary — treat it as unresolved, not as evidence either way.
  • Not narrowing the date range. Queries are capped at 1,000,000 records; wide protocol/date combinations can hit this cap silently. Narrow your date range and check result counts.
  • Relying on “places” in the Public Dev API. The docs page mentions it; the live spec does not define it. Don't build against it until you've confirmed it exists.

Documentation Gaps (for transparency)

These are gaps or inconsistencies in NASA/GLOBE's public documentation, not claims about the API's security or behavior. Full detail and sourcing is in docs/EVIDENCE_REGISTER.md.

  1. No authentication/authorization scheme is documented anywhere, yet 401/403 responses are declared on every operation.
  2. The OpenAPI response model (APIResponse) is an empty schema; real field names exist only in the PDF guide.
  3. The docs page promises a “places” capability in the Public Dev API that isn't in the live spec.
  4. Field casing differs between Data User Guide appendices (userID vs. userid).
  5. The docs page's worked example states a date range in prose ("1 January 2020 to 1 January 2012") that doesn't match the example URL's actual dates (2010-01-01 to 2012-01-02).
  6. What the userid field contains for measurements submitted via a GLOBE student account is not documented in any source reviewed.
